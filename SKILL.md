# Organizing Computational Biology Projects

Practical scaffolding and review guidance for structuring computational biology / bioinformatics
projects, distilled from Noble WS (2009), *A Quick Guide to Organizing Computational Biology
Projects*, PLoS Comput Biol 5(7): e1000424, https://doi.org/10.1371/journal.pcbi.1000424
(CC BY 4.0). The rules and structure below are the paper's; the wording, templates, and scripts
here are this repo's own.

## The two principles behind everything here

1. **Someone unfamiliar with the project — most often future-you — should be able to look at the
   files and understand in detail what was done and why.** Optimize for that reader, not for
   typing speed today.
2. **Everything you do, you will probably have to do over again.** New data arrives, a bug is
   found, parameters change. Organize and script things so redoing an experiment is cheap, not
   a reconstruction project.

Every recommendation below exists to serve one of these two goals. When a user's situation
doesn't fit a rule cleanly, reason from these principles rather than applying the rule rigidly.

## When to act vs. when to advise

- **New project, or user wants a starting structure** → offer to run `scripts/scaffold_project.py`
  to generate the skeleton (see below), then explain what goes where.
- **Existing/messy project** → don't blindly restructure. Read the current layout first (list
  directories, skim a few files), map what exists onto the structure below, and propose a
  concrete migration plan before moving anything. Reorganizing files is exactly the kind of
  action that can destroy in-progress work if done carelessly — confirm before moving or deleting
  anything non-trivial.
- **User is writing a driver/analysis script** → apply the driver-script rules and error-handling
  rules below directly to the code you write; use `assets/runall_template.sh` as a reference
  skeleton, not something to paste verbatim.
- **User asks a conceptual question** ("how should I organize this?", "what goes in version
  control?") → answer directly from the principles below; no need to touch the filesystem.

## Directory layout

At the project root, keep everything for one project together (the one exception: source code or
scripts genuinely shared *across* projects belong in their own project/repo, not copied into
each). Top level is organized **logically**, by type of thing:

```
myproject/
├── data/       fixed input data sets (raw, rarely modified)
├── results/    output of computational experiments
├── src/        source code
├── bin/        compiled binaries / installed scripts
└── doc/        one subdirectory per manuscript or writeup
```

Inside `data/` and `results/`, resist the urge to organize logically (e.g. one folder per
dataset or per method) — six months in, nobody remembers what `combined_v3_final` means, and you
rarely know in advance what experiments you'll actually end up running. Instead, organize
**chronologically**, one directory per date (`YYYY-MM-DD`, sorts correctly), optionally with a
short topic suffix:

```
data/2009-01-14/yeast/       results/2009-01-15/
                                ├── runall
                                ├── summarize
                                ├── split1/
                                ├── split2/
                                └── split3/
```

A single experiment often spans more than one day — don't create a new dated directory until you
actually start a new line of work. If the data/results split stops being useful for a project
(e.g. everything is generated fresh each time), it's fine to collapse both into a single
chronological `experiments/` directory instead.

Within one experiment directory, organization is logical again and depends on the experiment —
keep it flat until it grows unwieldy, then introduce structure. That structure should normally be
*generated by the driver script*, not built by hand (see below).

Every directory under `data/` should contain a **README** stating who downloaded/generated the
data, from what URL or source, and on what date — this is often the only provenance record that
will ever exist for that dataset. For very large or frequently-updated datasets a single README
stops being enough — treat it as a minimum, and reach for more systematic provenance tracking
(versioned manifests, a data pipeline that records its own inputs) as the dataset's size or churn
grows.

Use `scripts/scaffold_project.py` to generate this skeleton (including READMEs and a `.gitignore`)
in one step rather than creating it by hand — see "Scaffolding a new project" below.

## The lab notebook

Maintain one chronologically-ordered lab notebook per project, living at the root of `results/`
(`scaffold_project.py` creates `results/notebook.md`). Each entry:

- Is dated.
- Is verbose enough to stand alone — link to or embed the plots/tables it discusses.
- Records not just what was done, but *observations, conclusions, and ideas for future work*.
- **Especially covers failed experiments.** It's tempting to just link the bad plot and move on;
  instead, write down how you know it failed — that interpretation is often not obvious to a
  later reader (including future-you).
- Optionally captures relevant conversation notes or emails, so the notebook is a complete record
  of how the project evolved, not just of the commands run.
- Is written more verbosely, with less jargon, when the audience includes wet-lab collaborators
  rather than only other computational people — err toward over-explaining for that reader.

If the user is collaborating with others, suggest putting the notebook somewhere shareable
(a private wiki, a rendered HTML/markdown page, a hosted doc) rather than treating a plain local
file as the final form — but a markdown file in the repo is a perfectly good starting point.
`assets/notebook_template.md` has a ready-made entry format.

## Carrying out one experiment: the driver script

For each experiment, record every command either in a plain `README` of commands run, or —
preferably, once there's more than a couple of steps — in a **driver script**, conventionally
named `runall`. The lab notebook holds the prose account of an experiment; the driver script
holds every operational detail needed to reproduce it exactly. Apply these rules when writing one:

1. **Record every operation.** If it happened, it's in the script — nothing was done by hand off
   to the side.
2. **Comment generously.** A driver script is usually glue around other scripts/utilities rather
   than complex logic — write it so someone can follow what's happening from the comments alone.
3. **Never hand-edit intermediate files.** A hand-edit means the script is only semi-automatic;
   next time you'll have to redo the edit. Prefer `sed`, `awk`, `grep`, `cut`, etc. inside the
   script.
4. **Centralize file and directory names.** Keep all path names in the driver script and pass
   them down to any scripts it calls, rather than letting each sub-script hardcode its own paths.
   One place to update beats several.
5. **Use relative paths within the project.** Absolute paths break the moment someone else checks
   out the project (or you move it, or restore it from version control) into a different
   location.
6. **Make it restartable.** Wrap expensive steps as `if <output file missing>: <do the work>`.
   To rerun a step, just delete its output — don't rerun the whole pipeline from scratch.

For longer-running experiments, split into two scripts: `runall` (does the work, calling
`summarize` as its final step) and `summarize` (produces a plot/table/HTML page reporting
progress, and should degrade gracefully on a *partially* completed run so you can check in on
long jobs). `assets/runall_template.sh` and `assets/summarize_template.sh` demonstrate this shape
— adapt them to the user's actual language/tooling (shell, Python, R, Snakemake/Nextflow, etc.)
rather than forcing shell where it doesn't fit; the six rules above are the point, not the
specific syntax. Start with the simplest tool that can do the job — often shell — and move to a
more capable language only once the logic actually demands it; don't reach for machinery the
experiment doesn't need yet.

## Handling and preventing errors

1. **Detect errors, don't assume clean input.** Validate parameters and input; prefer robust
   library parsers over ad hoc ones for standard formats.
2. **Abort loudly on error.** Print to stderr and exit non-zero rather than limping onward —
   silently continuing past a failure risks drawing conclusions from a broken run. Check the
   return codes of everything the script calls.
3. **Write outputs atomically.** Write to a temp name, then rename to the final name once
   complete. This is also what makes rule 6 above (restartability) safe — a half-written file
   can never be mistaken for a finished one.

## What kind of script is this?

Useful to name explicitly when discussing structure with the user, since it affects where a
script should live:

| Type | Scope | Typical location |
|---|---|---|
| Driver script | Runs one experiment top-to-bottom | The experiment's own dated directory |
| Single-use script | One-off helper (e.g. reformat one file) | Next to the driver script that calls it |
| Project-specific script | Reused across experiments *within* this project | `bin/` or `src/`, just below project root |
| Multi-project script | Generic utility (FASTA extraction, ROC curves, k-fold splitting) | The user's personal toolkit repo, outside any one project |

Whatever the type, every script — however small — should support a usage/help flag that makes
its inputs, outputs, and options clear without reading the source.

## Version control

Recommend version control (git, in most modern contexts) for every project; if the project
doesn't have a repo yet, offer to `git init` one (never force-push or rewrite history without
being asked). It earns its keep three ways: backup, historical record (checkpoint your way back
to the exact state behind a three-month-old result), and collaboration.

Two habits matter more than the tool choice:

- **Commit at least daily.** Infrequent commits mean an incomplete history and a stale backup.
  Mid-flight/broken work is fine to commit on a branch — that's what branches are for.
- **Only version-control what you edit by hand.** Source, scripts, docs, the manuscript — yes.
  Compiled binaries and computed results — no: they bloat the repo (especially binary diffs,
  which store a full copy per version), get duplicated across every checkout, and change on every
  rerun anyway. Small, genuinely static data files are a reasonable exception; large or
  frequently-regenerated outputs are not.

`scaffold_project.py` writes a starter `.gitignore` (from `assets/gitignore_template`) that
excludes `results/` outputs by pattern (with `results/notebook.md` allow-listed back in) and
`bin/` binaries, plus a commented-out block to exclude `data/` entirely except its READMEs —
uncomment that block for projects whose raw data is large or frequently regenerated; leave it
off (the default) for projects where `data/` holds small, static files worth tracking directly.
Adjust the whole file to the user's actual toolchain.

## Scaffolding a new project

Run:

```bash
python "scripts/scaffold_project.py" --root <path/to/new/project> [--name <project-name>]
```

This creates the `data/ results/ src/ bin/ doc/` skeleton, a starter `results/notebook.md` from
the notebook template, a `.gitignore`, and a top-level `README.md` stub. It's intentionally a thin
wrapper around plain directory/file creation (see the script's `--help`) — read it before running
if the user wants to know exactly what it does, and feel free to adapt paths afterward.

To scaffold just a new dated experiment inside an existing project:

```bash
python "scripts/scaffold_project.py" --experiment --root <path/to/existing/project> [--topic <short-topic>]
```

This adds `data/<YYYY-MM-DD>[-topic]/` and `results/<YYYY-MM-DD>[-topic]/` (with `runall` and
`summarize` stubs copied from `assets/runall_template.sh` and `assets/summarize_template.sh`)
without touching the rest of the project.

## Reviewing an existing project

When asked to audit or clean up a project, check it against this list and report findings rather
than silently rewriting everything:

- [ ] Is there a single root directory containing everything for this project?
- [ ] Do `data/` and `results/` (or a merged `experiments/`) use chronological, not logical,
      naming?
- [ ] Does every raw dataset have a README with source/URL/download date?
- [ ] Is there a lab notebook, and is it actually being written to (not just created once)?
- [ ] Do experiments have a driver script, or at minimum a README of commands run — and does it
      use relative paths and centralized filenames?
- [ ] Is anything computed/generated currently sitting in version control that shouldn't be
      (large binaries, results that get regenerated), or conversely, are hand-edited files
      missing from it?
- [ ] Are commits happening regularly, or are there large uncommitted spans of work?

Surface concrete gaps with file paths, and propose a migration plan for the user to approve before
moving or deleting anything.
